# `useRouter` has more than `push`

`router` is the same object on every call to `useRouter()` — `push` is just
the method `ExpensesTableRow` happened to need. A few others show up
constantly once components get interactive:

<small>

```tsx
const router = useRouter();

router.push('/expenses/42'); // navigate, add a history entry
router.replace('/expenses/42'); // navigate, no new history entry
router.back(); // like clicking the browser's back button
router.forward(); // like clicking the browser's forward button
router.refresh(); // re-run Server Components for this route, keep client state
```

</small>

- **`replace`** — same as `push`, minus the history entry. Perfect for a
  "cancel and go back to the list" button after submitting a form: you don't
  want **Back** to return the user to the half-filled form.
- **`back` / `forward`** — programmatic equivalents of the browser's own
  buttons. Handy for a custom **"‹ Back to employees"** control that should
  behave exactly like the real back button, history and all.
- **`refresh`** — re-fetches data and re-renders Server Components for the
  current route **without** losing client state (an open dropdown, scroll
  position). It clears the client-side cache for that route, but does *not*
  invalidate anything cached on the server — that's what `revalidatePath` /
  `revalidateTag` are for, in module 07.

Notes:

Don't demo revalidatePath here — it needs Server Actions and caching, both unmet. The one thing worth landing: refresh() is a client-triggered re-render, not a cache invalidation, and that distinction matters a lot once caching shows up in module 07.
